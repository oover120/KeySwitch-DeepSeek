# KeySwitch.Hooks — заметки по реализации

Слой Windows (`src/KeySwitch.Hooks`, net8.0-windows, `RootNamespace = KeySwitch.Hooks`).
Сборка: `dotnet build src/KeySwitch.Hooks -v q` → 0 ошибок, 0 предупреждений.
Смоук-проверка — отдельный временный проект вне репозитория (`%TEMP%\keyswitch-smoke`),
все сценарии проходят; в репозиторий тесты слоя не добавлялись (тесты — зона тест-агента).

## Состав

| Файл | Назначение |
| --- | --- |
| `NativeMethods.cs` | P/Invoke, структуры Win32 (`KBDLLHOOKSTRUCT`, `INPUT`, `DROPFILES`), константы |
| `LayoutIds.cs` | Преобразование HKL ↔ идентификатор раскладки (`en-US`, `ru-RU`, `0xXXXX`), KLID ↔ langId |
| `KeyboardHookEventArgs.cs` | Событие хука (свойства строго по контракту + `Handled`) |
| `KeyboardHook.cs` | WH_KEYBOARD_LL на собственном потоке с message loop |
| `InputSender.cs` | `SendInput`, маркер `InjectionMarker`, ввод Unicode/Backspace/терминатора |
| `LayoutSwitcher.cs` | Чтение и смена раскладки окна/потока |
| `WindowInspector.cs` | Снимок окна переднего плана с кэшем 200 мс |
| `UiAutomationProbe.cs` | UIA-проба поля пароля/текстового поля на MTA-потоке |
| `ElevationHelper.cs` | Признак повышения прав, автозапуск (HKCU Run и schtasks) |
| `ClipboardHelper.cs` | Снимок/восстановление буфера обмена (чистый Win32) |

## Решения

### KeyboardHook

- Хук живёт в отдельном фоновом потоке с циклом `GetMessage`/`TranslateMessage`/`DispatchMessage`.
  Поток не зависит от UI-потока: занятое окно приложения не останавливает обработку.
- Очередь сообщений потока создаётся принудительно (`PeekMessage(..., PM_NOREMOVE)`) до
  `SetWindowsHookEx`: иначе `PostThreadMessage(WM_QUIT)` из `Stop()` мог бы потеряться, и поток
  завис бы в `GetMessage`.
- `Start()` синхронный: ждёт сигнала потока (до 5 с) и бросает `InvalidOperationException`
  с внутренней ошибкой, если `SetWindowsHookEx` вернул `NULL`. Повторный `Start()` — no-op.
- `Stop()`: 3 × `WM_QUIT` + `Join(200)`; если поток не завершился — аварийно снимает хук
  из другого потока (Win32 это разрешает), снова шлёт `WM_QUIT` и ждёт `Join(1000)`.
  Защита от `Stop()` внутри обработчика `KeyEvent` (поток не join-ит сам себя).
- `Start`/`Stop`/`Dispose` сериализованы одним lock: параллельный `Start` не создаст второй хук,
  пока старый поток ещё не завершился. Смоук-тест гоняет `Start`/`Stop` из четырёх потоков
  одновременно — падений и зависаний нет.
- Сигнал о завершении старта ставится безопасно: `Dispose()` мог освободить событие раньше,
  чем поток успел его выставить, — `ObjectDisposedException` в фоновом потоке недопустим.
- Состояния модификаторов читаются `GetAsyncKeyState` на момент события (глобальное состояние
  ввода, а не состояние очереди потока хука).
- CapsLock: `GetAsyncKeyState(VK_CAPITAL) & 0x0001` — младший бит даёт текущее состояние
  тумблера. `GetKeyState(VK_CAPITAL)` на потоке хука показывает состояние клавиши в очереди
  этого потока и для хука не годится.
- `Character`: сначала `LayoutCatalog.TryGet(layoutId)` + `LayoutTable.TryMap`; для букв
  регистр = `shift XOR capsLock`, для остальных символов CapsLock не влияет. Если таблицы нет
  или символа нет — `ToUnicodeEx` с HKL активного потока и собственной копией `byte[256]`:
  `GetKeyboardState` на потоке хука вернуло бы состояние его собственной очереди, поэтому
  состояние собирается вручную (Shift/Ctrl/Alt/CapsLock). Флаг `0x04` (NoStateChange) не даёт
  `ToUnicodeEx` испортить внутреннее состояние dead-key; возврат `-1` (dead key) и `0` → `Character = null`.
- Раскладка определяется по HKL *потока* окна переднего плана:
  `GetForegroundWindow` → `GetWindowThreadProcessId` (возвращает id потока, process id — в `out`)
  → `GetKeyboardLayout(threadId)`. Использование `out`-параметра как thread id — ошибка,
  она была найдена и исправлена.
- Свои синтетические события (`LLKHF_INJECTED` + `dwExtraInfo == InputSender.InjectionMarker`)
  не поднимаются в `KeyEvent`, но и **не глушатся**: вызывается `CallNextHookEx`, чтобы
  исправленный ввод дошёл до приложения. Чужие инъекции поднимаются как обычно с `IsInjected = true`.
- `Handled = true` → обработчик возвращает `1` (событие глушится).
- Исключения подписчика не пересекают границу с нативным кодом: ловятся, складываются в
  `LastError`, событие пропускается дальше. Хук при этом остаётся жив.

### InputSender

- Маркер `InjectionMarker = 0x4B53_0001` пишется в `dwExtraInfo` каждого события.
  `KEYEVENTF_INJECTED` в `dwFlags` не существует — `LLKHF_INJECTED` выставляет сама Windows
  для любого `SendInput`; поэтому маркер — единственный способ отличить свои события.
- Пакет событий отправляется одним `SendInput`: для Backspace+текста это гарантирует
  отсутствие пользовательских событий между ними (требование контракта).
- `SendText` — по два события `KEYEVENTF_UNICODE` на code unit (суррогатная пара — двумя
  code unit'ами), `wVk = 0`.
- Терминатор: пробел/`\r`/`\n`/Tab — через виртуальные клавиши (приложения ждут `WM_KEYDOWN`),
  прочие символы — через Unicode.
- Все вызовы под одним lock; результат `SendInput` не ретраится вслепую (можно задвоить текст).

### LayoutSwitcher

- Раскладка хранится по потокам, а не системно: `GetLayoutId`/`Ensure` читают
  `GetKeyboardLayout(threadId окна)`.
- `SwitchTo`: `PostMessage(WM_INPUTLANGCHANGEREQUEST, 0, hkl)` в окно, затем опрос смены
  каждые 5 мс до 60 мс; если не сменилось — `AttachThreadInput` + `ActivateKeyboardLayout`
  (2 попытки) и снова ожидание. Возвращает фактический результат проверки.
- `Ensure` не переключает, если раскладка уже нужная (лишний Shift пользователю не нужен).
- HKL ищется среди загруженных (`GetKeyboardLayoutList`), при отсутствии — `LoadKeyboardLayout("00000419")`.
- Для консольных окон (`ConsoleWindowClass`, `CASCADIA_HOSTING_WINDOW_CLASS`) адресат сообщения —
  `GetConsoleWindow()`; если своего консольного окна у процесса нет — сообщение идёт в само окно.

### WindowInspector

- Кэш 200 мс по handle: хук спрашивает снимок на каждое нажатие, а разбор процесса и токена дорогой.
- Процесс мог завершиться между `GetForegroundWindow` и `Process.GetProcessById` — все
  обращения в try/catch, при неудаче поля остаются пустыми, исключения наружу не выходят.
- Путь к exe: `Process.MainModule.FileName`, при отказе — `QueryFullProcessImageName`
  через `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`.
- `IsElevated`: `OpenProcess` + `OpenProcessToken(TOKEN_QUERY)` + `GetTokenInformation(TokenElevation)`.
  Если доступ к токену закрыт (`ERROR_ACCESS_DENIED`), процесс считается повышенным:
  обычные процессы читаются без отказа.
- `IsFullscreen`: `GetWindowRect` против `rcMonitor` (`MonitorFromWindow`, допуск 2 px);
  иначе эвристика — `WS_POPUP` без `WS_CAPTION` и ≥ 95% площади монитора.
- `IsConsole`: `GetConsoleWindow() == hwnd` либо класс окна из списка консольных.

### UiAutomationProbe

- Выделенный MTA-поток + ограниченная очередь (16). Поток хука ждёт ответ не дольше 30 мс.
- Кэш по hwnd на 1 с; при таймауте и переполнении очереди отдаётся закэшированное значение,
  при исключениях/недоступности UIA — `false` (лучше пропустить исправление, чем блокировать ввод).
- После таймаута — пауза 500 мс перед следующим запросом: иначе каждое нажатие платило бы
  те же 30 мс ожидания.
- Проверка «фокус в нашем окне»: сравнение `ProcessId` с процессом окна и обход
  `TreeWalker.ControlViewWalker` до 12 уровней (у браузеров `NativeWindowHandle` часто 0 —
  тогда доверяем `ProcessId`).
- `IsTextInput`: `IsKeyboardFocusable` и доступный `ValuePattern`/`TextPattern` либо
  `ControlType` Edit/Document; для парольных полей принудительно `false`.

### ElevationHelper

- Автозапуск: ключ `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, значение `"KeySwitch"`
  = `"<путь>"`; снятие — `DeleteValue(throwOnMissingValue: false)`.
- Планировщик: `schtasks.exe` из `%SystemRoot%\System32` через `ProcessStartInfo`
  (`UseShellExecute = false`, `CreateNoWindow`, `WindowStyle.Hidden`, перехват stdout/stderr,
  `WaitForExit(10_000)`), успех — `ExitCode == 0`; `-1` — не удалось запустить.
  Команды: `/Query /TN "KeySwitch"`, `/Create /TN "KeySwitch" /TR "\"<exe>\"" /SC ONLOGON /RL HIGHEST|LIMITED /F`,
  `/Delete /TN "KeySwitch" /F`.
- `EnableScheduledAutostart(runAsAdmin: true)` требует запуска из процесса администратора —
  иначе `schtasks` вернёт ненулевой код, и метод вернёт `false`.

### ClipboardHelper

- Снимок и восстановление всех сериализуемых форматов: Unicode-текст, список файлов
  (`CF_HDROP`), изображение (`CF_DIB`/`CF_DIBV5`, байты в base64), HTML и RTF
  (зарегистрированные форматы, байты в base64). Снимок — JSON-строка (для вызывающего —
  непрозрачная), лимит 8 МБ на формат.
- Все операции — на выделенном STA-потоке с прокачкой сообщений и таймаутом 3 с:
  буфер обмена нельзя трогать с потока хука.
- **Реализация переписана на прямой Win32.** WPF-обёртка `System.Windows.Clipboard`
  в этом окружении бросает `COMException` «Ошибка при вызове OpenClipboard (0x800401D0
  CLIPBRD_E_CANT_OPEN)» на любой вызов, даже на собственном STA-потоке после
  `OleInitialize` и прокачки сообщений, тогда как сырые `OpenClipboard`/`SetClipboardData`/
  `GetClipboardData` на том же потоке работают. Поэтому используются
  `OpenClipboard` (с ретраями 10 × 30 мс), `EmptyClipboard`, `EnumClipboardFormats`/
  `IsClipboardFormatAvailable`, `GetClipboardData` + `GlobalLock/GlobalSize`, запись —
  `GlobalAlloc(GMEM_MOVEABLE)` + `SetClipboardData`; при ошибке `SetClipboardData` память
  освобождается, при успехе ею владеет система.
- Для `CF_HDROP` собирается структура `DROPFILES` (`pFiles = sizeof(DROPFILES)`, `fWide = 1`)
  с путями UTF-16 и двойным нулём в конце.
- `RestoreAll(null)` и пустой снимок — no-op; частичные ошибки глотаются (восстанавливается
  то, что удалось). `SetText("")` очищает буфер; `GetText()` возвращает `null`, если текста нет.

## Отклонения от контракта

Все отклонения — только аддитивные расширения, сигнатуры контракта не менялись.

1. `KeyboardHookEventArgs` получил **публичный конструктор** (в контракте — только get-свойства).
   Нужен тестам и эмуляции событий; порядок параметров соответствует порядку свойств.
   В `ToString()` символ намеренно не выводится, чтобы ввод не попадал в логи.
2. `KeyboardHook.LastError` — последнее исключение подписчика `KeyEvent`. Исключения ловятся
   внутри хука (иначе они уронили бы процесс), но не теряются молча.
3. `InputSender.SendCorrection(int backspaces, string text)` — Backspace и текст одним вызовом
   `SendInput`. Контрактный порядок «одним пакетом» через отдельные `SendBackspaces` + `SendText`
   недостижим: между ними неизбежен разрыв, в который может вклиниться пользовательский ввод.
   Приложение может продолжать использовать `SendBackspaces` + `SendText`, но для гарантии
   контракта следует вызывать `SendCorrection`.
4. `SendKeyStroke(virtualKey, shift, keyUp)` трактуется буквально: **одно** событие — нажатие
   или отпускание (если `shift` — с зажатием/отпусканием Shift вокруг). Полная пара
   down+up — это два вызова.
5. CapsLock в вычислении `Character`: для букв регистр = `shift XOR capsLock`, для остальных
   символов CapsLock не учитывается (соответствует поведению Windows); в `ToUnicodeEx` состояние
   CapsLock передаётся как обычно.
6. `GetKeyState(VK_CAPITAL)` заменён на `GetAsyncKeyState(VK_CAPITAL) & 0x0001` (см. выше:
   на потоке хука `GetKeyState` возвращает состояние чужой очереди).
7. `ToUnicodeEx` вызывается с собственной копией состояния клавиатуры, а не с `GetKeyboardState`:
   состояние последнего не годится для потока хука. Дополнительно используется флаг `0x04`
   (NoStateChange), чтобы не портить состояние dead-key.
8. Свои синтетические события хук **пропускает дальше** (`CallNextHookEx`), а не глушит:
   исправленный текст должен дойти до приложения. `IsOurEvent` в `KeyEvent` всегда `false` —
   такие события в событие не попадают вовсе.
9. `ClipboardHelper` не использует `DataObject`/`Clipboard.GetDataObject()`, как предполагалось
   в задании, — из-за нерабочей WPF-обёртки (см. «Решения»). Снимок — JSON, формат внутренний
   и вызывающему коду не важен.
10. `UiAutomationProbe` получил паузу 500 мс после таймаута UIA (сверх «вернуть закэшированное»):
    иначе каждое нажатие в медленном приложении ждало бы 30 мс в хуке.
11. `WindowInspector`/`ElevationHelper`: при `ERROR_ACCESS_DENIED` процесс считается повышенным
    (консервативно: раз токен не прочитать, исправлять ввод в нём нельзя).

## Что проверить вручную

Автотесты проверяют классы на синтетических событиях и реальном рабочем столе, но не могут
проверить полноценный пользовательский сценарий. Ниже — обязательный ручной чек-лист.

1. **Хук и «свои» события.** Открыть Блокнот, набрать текст в неверной раскладке — исправление
   должно вставиться один раз, без повторной обработки собственного ввода (нет зацикливания,
   нет мигания раскладки). Отдельно проверить, что хук видит обычные нажатия (счётчик событий
   в отладке), но не реагирует на `SendText`.
2. **Переключение раскладки.** `Ensure`/`SwitchTo` в Notepad, Chrome, Проводнике, Word:
   раскладка должна смениться у активного окна (проверять значок языка). Повторный `Ensure`
   с текущей раскладкой не должен слать лишний Shift. Проверить оба направления RU↔EN.
3. **Консольные окна.** Windows Terminal (`CASCADIA_HOSTING_WINDOW_CLASS`) и классический
   conhost: ввод в PowerShell/cmd, исправление — смена раскладки должна доходить.
4. **Парольные поля.** Chrome (вход), 1Password, окно входа Windows: `IsPasswordField` = `true`,
   исправление не выполняется. Проверить, что UIA не тормозит ввод (нет лагов на каждом нажатии).
5. **Полноэкранные приложения.** Игра/видео на весь экран: `IsFullscreen` = `true`,
   поведение KeySwitch — по решению App (обычно не вмешиваться).
6. **Буфер обмена.** Скопировать картинку (Win+Shift+S), файлы в Проводнике, HTML-фрагмент
   из браузера: `CaptureAll` → `SetText` → `RestoreAll` → содержимое буфера должно вернуться
   (картинка — вставляться, файлы — вставляться списком). Отдельно: буфер занят другим
   приложением (например, RDP-буфер) — вызовы не должны вешать приложение.
7. **Автозапуск.** `SetRunKeyAutostart(true)` → проверить `HKCU\...\Run` в regedit и вход
   в систему; `SetRunKeyAutostart(false)` → значение удалено.
   `EnableScheduledAutostart(false)` из обычного процесса, затем `(true)` из процесса
   администратора: `schtasks /Query /TN KeySwitch` показывает задачу, уровень прав
   соответствует `runAsAdmin`. `DisableScheduledAutostart` удаляет задачу.
8. **Повышенные процессы.** Запустить KeySwitch без прав и проверить `IsProcessElevated`
   у окна администратора (например, `cmd` от администратора): должно быть `true`,
   и приложение не должно пытаться вводить туда текст (UIPI заблокирует `SendInput`).
9. **Завершение процесса.** Закрыть приложение, чьё окно было активным, в момент работы
   хука: `WindowInspector` не должен бросать исключения (поля процесса могут быть пустыми).
10. **Стресс жизненного цикла.** Многократные `Start`/`Stop`/`Dispose` (например, из настроек)
    не должны оставлять висящих потоков/хуков: количество потоков процесса не растёт.

## Не сделано / ограничения

- **Логирование намеренно отсутствует**: слой не пишет на диск ни события клавиш, ни их
  содержимое (требование ТЗ). Технические ошибки доступны только через `KeyboardHook.LastError`.
- **Проект не добавлен в `KeySwitch.sln`** — файл solution вне зоны Hooks; правку должен
  сделать владелец solution (lead/App).
- **Форматы буфера обмена**: `CF_BITMAP` не сохраняется (GDI-хэндл не сериализуем; изображение
  покрывается `CF_DIB`/`CF_DIBV5`), произвольные зарегистрированные форматы — только
  `HTML Format` и `Rich Text Format`.
- **`IsTextInput`** — эвристика UIA: в кастомных контролах и при недоступном UIA возможен
  `false` (исправление просто не выполнится).
- **UIA-таймаут** (30 мс) может дать устаревший ответ на первом нажатии после смены фокуса:
  если фокус только что перешёл в парольное поле, первый символ может быть обработан по
  старому кэшу. Риск осознан, отдельного «безопасного» ответа контракт не предусматривает.
- **Хук уровня WH_KEYBOARD_LL** не работает, если процесс запущен в другом сеансе
  (например, служба), и не получает ввод, когда рабочий стол заблокирован (UAC/secure desktop).
- **`SendInput` в окна с более высоким integrity level** блокируется UIPI — это ограничение
  Windows, а не реализация; App должен ориентироваться на `IsElevated`.
- **Смены раскладки в консоли** зависят от того, обрабатывает ли конкретный хост
  `WM_INPUTLANGCHANGEREQUEST`; консервативный fallback — `ActivateKeyboardLayout` на потоке.
- **`ClipboardHelper` не потокобезопасен по формату снимка** между версиями приложения:
  формат помечен `version = 1`, при изменении модели старые снимки следует считать несовместимыми.
