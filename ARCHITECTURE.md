# Архитектура KeySwitch

KeySwitch — трей-приложение Windows 11, которое в реальном времени исправляет слова,
набранные не в той раскладке (RU ↔ EN). Приложение работает локально, без сети и
телеметрии, и не сохраняет текст набора.

## 1. Общая картина

```
┌──────────────────────────────────────────────────────────────────────┐
│ KeySwitch.App (WPF-окна + трей на Win32 Shell_NotifyIcon)             │
│  AutoSwitchService · TrayService · SoundService · AutostartService    │
│  Views / ViewModels / Themes (WPF, стиль Windows 11)                  │
└───────────────┬───────────────────────────────┬──────────────────────┘
                │                               │
      ┌─────────▼──────────┐          ┌─────────▼──────────┐
      │ KeySwitch.Hooks    │          │ KeySwitch.Data     │
      │ WH_KEYBOARD_LL     │          │ настройки, словари │
      │ SendInput          │          │ n-граммы, обучение │
      │ LayoutSwitcher     │          │ исключения, логи   │
      │ UIA / окна / DPI   │          │ ассеты (встроены)  │
      └─────────┬──────────┘          └─────────┬──────────┘
                │                               │
                └───────────┬───────────────────┘
                            │
                  ┌─────────▼──────────┐
                  │ KeySwitch.Core     │
                  │ буфер слова        │
                  │ таблицы раскладок  │
                  │ детектор языка     │
                  │ движок исправлений │
                  └────────────────────┘
```

Правило зависимостей: `Core` не знает про Windows (кроме структур VK-кодов, которые
передаются как `int`), `Data` не знает про UI, `Hooks` не знает про настройки,
`App` — единственное место, где всё связывается.

## 2. Проекты

## 3. Путь одного нажатия

```
WH_KEYBOARD_LL callback (поток хука)
  └─ KBDLLHOOKSTRUCT → KeyboardHookEventArgs (VK, scancode, модификаторы, символ)
       └─ AutoSwitchService.OnKeyEvent  (синхронно, < 5 мс)
            ├─ наше синтетическое событие? → игнор
            ├─ окно/процесс в исключениях, полноэкранная игра, поле пароля → по режиму
            ├─ KeyClassifier.Classify → WordChar | Terminator | Backspace | Reset | Ignore
            ├─ WordChar → CorrectionEngine.AppendChar → (опция) TryEarlySwitch
            ├─ Terminator → CorrectionEngine.CompleteWord
            │     └─ план есть → args.Handled = true, план в очередь выполнения
            └─ Reset → CorrectionEngine.Reset
```

Выполнение плана идёт вне потока хука:

```
CorrectionWorker (фоновый поток + очередь)
  ├─ LayoutSwitcher.SwitchTo(hwnd, targetLayout)   // до ввода, чтобы символы попали в нужную раскладку
  ├─ InputSender.SendBackspaces(plan.DeleteCount)
  └─ InputSender.SendText(plan.TextToType)          // Unicode, терминатор уже внутри
       └─ все события помечены dwExtraInfo = InjectionMarker, хук их отбрасывает
```

Нажатия пользователя, пришедшие во время выполнения плана, складываются в очередь и
воспроизводятся после — быстрый набор не теряется.

## 4. Потоки и синхронизация

| Поток | Что делает |
|---|---|
| Поток хука (отдельный, с message loop) | Принимает `WH_KEYBOARD_LL`, поднимает `KeyEvent`, глушит событие при `Handled`. |
| UI-поток WPF | Скрытое Win32-окно трея, окна настроек, таймер обновления иконки. |
| Correction worker | Выполняет планы, держит очередь отложенных нажатий. |
| Фоновый загрузчик ассетов | `LanguageResources.Load` при старте, не блокирует трей. |
| STA-поток буфера обмена | `ClipboardHelper` (буфер обмена требует STA). |

Общие данные: настройки (`SettingsStore`) читаются под `lock`, изменяются только из UI;
`CorrectionEngine` живёт на потоке хука и не разделяется между потоками; обучение
(`LearningStore`) пишется из worker'а под собственной блокировкой и сохраняется
асинхронно (debounce 2 с).

## 5. Данные на диске (`%APPDATA%\KeySwitch\`)

| Файл | Содержимое |
|---|---|
| `settings.json` | Настройки (см. `docs/CONTRACTS.md`). |
| `exceptions.json` | Правила процессов, слова-исключения, пользовательские папки. |
| `learning.json` | Слова и счётчики отмен/принятий. Контекст и история не хранятся. |
| `typos-ru.txt`, `typos-en.txt` | Редактируемые списки замен `неверно=верно`. |
| `logs\keyswitch.log` | Технические события, без текста набора. Ротация 2 МБ. |
| `sounds\` | Пользовательские wav. |

Встроенные ассеты (словари, n-граммы, ё-словарь, лицензии) лежат в
`KeySwitch.Data` как `EmbeddedResource` и распаковываются в память при старте.

## 6. Определение раскладки и переключение

Раскладка в Windows хранится **по потокам**, поэтому:

1. `GetForegroundWindow` → `GetWindowThreadProcessId` → `GetKeyboardLayout(threadId)` — раскладка
   активного окна, а не системы.
2. Переключение: `PostMessage(hwnd, WM_INPUTLANGCHANGEREQUEST, 0, hkl)` (для консольных окон —
   в `GetConsoleWindow()`), затем проверка `GetKeyboardLayout` с ожиданием до 60 мс.
3. Символ нажатия вычисляется по таблице раскладки (детерминированно), `ToUnicodeEx` —
   только как fallback для незнакомых раскладок.

## 7. Расширяемость на третий язык

Ядро не содержит знаний о конкретных языках, кроме каталога таблиц:

- `LayoutTable` — физическая карта клавиш языка (`LayoutCatalog` добавляет новую таблицу);
- `ILanguageResourcesProvider` — словарь и n-граммы для языковой пары;
- `LayoutPairRegistry` — какие пары считаются альтернативными.

Добавление немецкого = новая `LayoutTable`, новый набор ассетов (`words-de`, `ngrams-de-*`),
регистрация пары `en-US ↔ de-DE`. Правок в `CorrectionEngine`/`LayoutDetector` не требуется.

## 8. Безопасность и приватность

- Нет сети: ни одного `HttpClient` в рантайме (только в `tools/BuildAssets`).
- Не логируется текст набора: в лог попадают только события (старт, смена раскладки,
  ошибка, счётчики), без буфера и без символов.
- Поля паролей: UIA `IsPassword` + эвристика «смешанный регистр + цифры/знаки, длина > 6»
  → слово не конвертируется, принудительно английская раскладка.
- Окна с повышенными правами (UIPI) хуком не видны — в трее показывается предупреждение,
  предлагается режим администратора через планировщик заданий.

## 9. Производительность

- Хук: O(1) на событие, без аллокаций в горячем пути (переиспользуемые буферы).
- Детектор: O(длина слова) с бинарным поиском по UTF-8 блобу словаря и по n-граммам.
- Память: словари хранятся компактно (UTF-8 блоб + смещения): 400 тыс. RU + 98 тыс. EN
  вместе с n-граммами, ё-словарём и обучением — **18 МБ managed heap**. Полный рабочий
  набор процесса при простое — **110 МБ** (self-contained .NET 8 + WPF + UI Automation);
  цель ТЗ ≤ 80 МБ не достигнута, разбор — в DECISIONS.md, D023. После первого открытия
  окна настроек WPF поднимает milcore/Direct3D и набор вырастает до ~190 МБ.
- Простой: никаких опросов, кроме таймера иконки 500 мс и обновления окна по событию фокуса.
